# 작업 분해 (Task Breakdown)

복잡한 개발 작업을 실행 가능한 작은 단계로 분해합니다.

## 🎯 작업 목표

**[여기에 작업 내용 입력]**

예시:
- 도시 상세페이지를 만들고 싶어
- Phase 3 필터바 UI 구현
- 사용자 프로필 편집 기능 추가

---

## 📋 분석 프로세스

당신은 복잡한 개발 작업을 실행 가능한 작은 단계로 분해하는 전문가입니다.
주어진 문제를 분석하고, SOLID 원칙을 준수하면서 점진적으로 구현할 수 있는 체계적인 계획을 수립하세요.

### 1단계: 현재 상태 파악
먼저 다음을 분석하세요:
- 관련 파일과 컴포넌트 식별
- 현재 데이터 구조 및 아키텍처
- 기존 코드의 패턴과 규칙
- 기술 스택 및 의존성

### 2단계: 영향 범위 분석
다음을 고려하여 영향 범위를 파악하세요:
- 변경이 필요한 파일 목록
- 영향받는 컴포넌트/모듈
- 연관된 테스트 파일
- 업데이트가 필요한 문서

### 3단계: 제약 조건 확인
다음 제약 조건을 고려하세요:
- SOLID 원칙 준수
- 기존 코드 패턴 유지
- 타입 안정성 보장
- 성능 영향 최소화

## 🔧 작업 분해 원칙

1. **원자성**: 각 작업은 하나의 명확한 목적만 가짐
2. **독립성**: 가능한 한 다른 작업과 독립적으로 실행 가능
3. **테스트 가능성**: 각 단계의 완료를 검증할 방법이 있어야 함
4. **점진성**: 각 단계 완료 후에도 시스템이 작동해야 함
5. **롤백 가능성**: 문제 발생 시 이전 상태로 복구 가능

## 📝 출력 형식

### 전체 개요
```
목표: [작업의 최종 목표]
예상 영향: [변경될 파일 수와 주요 컴포넌트]
난이도: [Low/Medium/High]
위험도: [Low/Medium/High]
```

### 의존성 다이어그램
```
작업 흐름도를 ASCII로 표현:
Task 1 → Task 2 → Task 4
    ↓       ↓
  Task 3 → Task 5
```

### 상세 작업 목록

각 Phase마다 다음 형식으로:

```
## Phase N: [Phase 이름]

### - [ ] 작업 N.M: [작업명]

**목적**: [이 작업이 왜 필요한가]

**변경 사항**:
- [ ] 파일1: 구체적인 변경 내용
- [ ] 파일2: 구체적인 변경 내용

**선행 조건**:
- 작업 X.Y가 완료되어야 함 또는 "없음"

**구현 가이드**:
1. 첫 번째 단계
2. 두 번째 단계
3. ...

**검증 방법**:
- [ ] TypeScript 타입 체크 통과 (`npx tsc --noEmit`)
- [ ] Lint 통과 (`npm run lint`)
- [ ] 빌드 성공 (`npm run build`)
- [ ] 수동 테스트: [구체적인 확인 방법]

**예상 시간**: [Small: <30분 / Medium: 30분-2시간 / Large: 2시간+]
**위험도**: [Low/Medium/High]
**영향 범위**: [파일 개수와 주요 컴포넌트 나열]
```

### 중간 검증 포인트

각 Phase 완료 후:
```
### ✅ Phase N 검증 체크리스트
- [ ] TypeScript 타입 체크 통과
- [ ] ESLint 오류 없음
- [ ] 개발 서버 정상 실행
- [ ] 빌드 성공
- [ ] 관련 기능 수동 테스트 완료
- [ ] 문서 업데이트 (필요시)
```

## 🚨 위험 요소 및 대응 전략

잠재적 문제점을 식별하고 대응 방안을 제시:

```
1. **[위험 항목]**
   - 발생 가능성: [Low/Medium/High]
   - 영향도: [Low/Medium/High]
   - 대응 방안: [구체적인 해결 방법]
```

## 📊 완료 기준

```
### 최종 검증 체크리스트
- [ ] 모든 타입 에러 해결
- [ ] Lint 경고 및 에러 없음
- [ ] 프로덕션 빌드 성공
- [ ] 모든 기능 정상 동작 확인
- [ ] 성능 저하 없음
- [ ] 문서 업데이트 완료
```

## 💡 구현 팁

1. **인터페이스 우선**: 데이터 구조 변경은 항상 인터페이스부터 수정
2. **타입 에러 추적**: 인터페이스 변경 후 타입 에러로 모든 영향 범위 파악
3. **점진적 적용**: 한 번에 하나의 컴포넌트만 수정
4. **자주 검증**: 작은 변경 후에도 타입 체크와 빌드 실행
5. **커밋 전략**: 각 Phase 완료 후 커밋으로 롤백 지점 확보

## 🔄 반복 개선

작업 계획 수립 후:
1. 각 작업이 너무 크지 않은지 검토 (30분-2시간 단위가 이상적)
2. 의존성이 복잡하면 작업 순서 재조정
3. 병렬 실행 가능한 작업 식별
4. 고위험 작업은 더 작은 단계로 분해
